# Issue loop

Act as coordinator for the repo given as the argument: `/issue-loop <repo> [version-key]`. Pull open issues and sort them into the execution queue by four keys, in order:

1. **Version** — see "Version scope" below. Absent an explicit version key, current-version labels sort first (e.g. `v1` when v1 is the launch scope) and later versions (`v2`) and `maybe-*` candidates wait unless the user pulls them in.
2. **Bug** — `bug`-labeled issues first within a version.
3. **Priority** — P0 → P1 → P2 within that (no priority label = P2).
4. **Filed date** — oldest first as the tiebreak.

## Version scope (the fence)

The second argument is an optional **version key** — a label name (`v2`, `web-redesign`, `launch`) that scopes the whole run.

- **No version key** (the default, for repos the loop owns outright): version is a *sort* key only. Unversioned issues stay eligible and queue behind current-version ones.
- **Version key given** (`/issue-loop my-repo web-redesign`): that label becomes a hard *filter*. Only open issues carrying it are eligible — everything else on the board is invisible for the run, including unlabeled issues, other versions, bugs, and P0s. Nothing outside the fence gets claimed, labeled, commented on, audited, or "checked on."

Fence any board the loop doesn't own outright — a shared team repo, a repo whose real work queue lives elsewhere (Asana, Linear), or a board that is mostly intake rather than planned work. Filing the scope under one label and fencing the run to it is what keeps the loop off someone else's backlog.

When fenced:

- **Verify the label exists on the repo before the first pick.** A typo'd fence matches nothing and the loop reports an empty board instead of a bad argument.
- **Re-apply the fence on every board re-pull**, not just the first. The re-sort every 2 issues filters first, then sorts.
- **Learn the repo's own park and claim labels and honor them inside the fence.** A shared board usually already has its own vocabulary for "a human owns this" (`decision`, `awaiting-user`, `blocked`) and "something else is already working this" (`fix-in-progress`, `in-progress`); read the label list up front and treat those as `skip-me`. Ask rather than guess when a label's meaning is ambiguous.
- **Confirm the merge policy before the first PR** when the repo has other active contributors authoring PRs, human or bot. Auto-merge is the default on a repo the user owns; on a shared `main` it needs the user's explicit go-ahead for the run.

Run two at a time: Claude subagent implements → `codex-review` reviews. Open PRs, merge automatically, watch deploys, continue until paused or empty. **Every 2 completed issues, re-pull the open board and re-sort before picking the next** — the user refiles and relabels mid-loop; a queue computed at session start is stale by definition.

## Roster (pinned — this loop's execution style)

- **The session's main agent holds the coordinator seat — whatever model it is** (Opus by default): scopes each issue, writes the implementer prompts, reads every diff, arbitrates review findings, merges, keeps the trail. The coordinator never implements — about to edit app code beyond a trivial review fix (~5 lines)? Stop: that's a subagent dispatch, not your edit.
- **A Sonnet subagent (`model: 'sonnet'`, pointed at the issue's worktree from rule 3) implements clear-spec and backend issues; an Opus subagent implements UI, copy, API-shape, and judgment-heavy issues.** Escalate a Sonnet attempt to Opus without asking when it misses the bar. UI issues verify via statics/build and the coordinator's diff read — never open a browser (Playwright, Chrome DevTools, `codex-computer-use`, or otherwise) unless the user asks for it during the session; when they do, the coordinator judges the screenshots against the mocks and iterates until they clear the taste bar. Screenshots go into the PR with `gh pr create --attach` / `gh pr edit --attach` (body references like `![alt](./x.png)` are rewritten to the uploaded URL) — never commit captures or push them to a side branch. Every implementer prompt says no new comments unless they state a non-obvious invariant.
- **Review: Codex via `codex-review`, every diff** — a fresh ephemeral run with an adversarial prompt, told to attack a specific checklist (correctness, scale smells, the issue's acceptance criteria, needless comments). A different model family from the implementer, in a fresh context. The coordinator may read trivial diffs (a few lines) directly instead. Either way the coordinating model verifies reviewer claims before acting — reviews and their test assertions can encode wrong expectations.
- Everything else the global instructions cover — code style, taste, PR/commit conventions, the fresh-context review rule — still governs; don't restate or relitigate it per issue.

## Before beginning

If you keep a session log or a project workspace, attach this run to it before starting — that's where rule 9's trail lands. The loop sends review through the `codex-review` skill from [dayton-agent-coordination](https://github.com/daytonbaird/dayton-agent-coordination); install it first.

**Establish the version before the first pick.** The queue's top sort key is the version label, so a run that guesses it burns down the wrong scope. A version key passed as the second argument settles it and turns on the fence — state it back before starting. With no argument, ask which version is in scope, whether the run is fenced or merely sorted, and whether later-version or `maybe-*` items should be pulled in. Re-confirm on any board re-pull that surfaces a version label you haven't seen.

## Rules

1. **The queue is law.** The fence first when the run has a version key, then the version → bug → priority → date sort above, two in flight. Never touch issues outside the fence, issues labeled `skip-me`, or anything explicitly parked by the user. Also skip **pre-launch items** — issues whose action is timed to launch (title/body says "before launch", "at launch", "until launch", or the work only makes sense as a launch step, e.g. clearing data or flipping a disabled feature on) — unless the user pulls them in during the session. One issue = one branch = one PR (`Closes #N`). The user must always be able to tell what's being worked on.
2. **Read each issue fresh from GitHub at dispatch time** — issues get edited; your memory of the backlog is stale by definition.
   - **Steer around other agents' lanes.** Before claiming, read the issues other agents have claimed (`in-progress` you didn't set). If your candidate plausibly touches the same files or surface as one of those (same route file, same view, same subsystem), pass over it silently — no label, no comment — and take the next queue item. Re-check on every board re-pull; a passed-over issue becomes eligible again once the conflicting claim clears.
   - **Claim before you touch.** Multiple agents may run this loop on the same repo concurrently. The moment you pick an issue — before the worktree, before the prompt — add the green `in-progress` label (create it once if missing: color `0E8A16`, description "An agent is actively working this issue — do not pick up"). An issue already labeled `in-progress` belongs to another agent: treat it exactly like `skip-me`, never audit or "check on" it. Remove the label whenever the issue leaves your hands — a `needs-human-review` hand-back, a park, an abandon, and also on completion: when a merged `Closes #N` closes the issue, strip `in-progress` right after the merge so closed issues never carry a stale claim. A claim you're no longer actively working is a lie — clean it up before ending the session or writing a handoff.
3. **Fresh worktree per issue, off `origin/main`.** Never work in the main checkout. Follow the repo's documented setup order. **Check for a repo-specific worktree carve-out first** — a repo whose checkout is large enough that a worktree is expensive (a big monorepo) may call for a sparse-checkout worktree or serial work on a branch in the main checkout instead. Absent a carve-out, this rule stands as written.
4. **The implementer gets a self-contained prompt**: repo context, acceptance criteria from the issue, the repo's standing constraints and known footguns, exact verification commands, a report-file path. Subagents don't read the global instructions or repo context — the prompt carries both. A vague prompt costs a full round trip. **If the repo keeps topic docs (a `docs/` dir, an AGENTS.md "keep docs true" rule), the prompt names the docs the change plausibly touches and requires updating them in the same diff** — implementers never update docs unprompted, and the coordinator checks doc truth at review: a behavior change that contradicts a documented claim is a review finding, same severity as a failing test.
5. **One test-harness owner at a time.** If the repo's e2e suite binds fixed ports, only one concurrent run may use it; the other runs static checks and the coordinator runs its suite serially before merge.
6. **Every diff gets adversarial review per the roster** — a `codex-review` pass with an attack checklist, with the coordinating model verifying reviewer claims always. Review findings go back to the implementing subagent (via `SendMessage`, context intact) or get fixed inline; re-verify after.
7. **Serial merges; watch every deploy to completion.** A green merge means nothing until CI finishes. If two branches touched generated files, regenerate on merged main and run the combined suite once.
8. **P0s break every rule except verification and the fence.** Fix inline if fastest, but reproduce the exact failing condition before and after — never ship a P0 fix on reasoning alone. A P0 outside the run's version fence is still out of scope: surface it to the user and let them pull it in or start a separate run.
9. **Leave a trail as you go** — session log per landing, durable lessons to agent memory. The loop survives sessions only if the state does.
10. **Spike tickets resolve as a comment on the issue.** A `spike`-labeled issue is a research dispatch (a Sonnet subagent, Opus when it needs judgment), not a build — no branch, no PR. The deliverable is a findings comment posted on the issue itself: answers with file:line citations, verified-vs-inferred distinguished, and any questions that still need a human owner. When the findings comment is posted, tag the issue `needs-human-review` and move on — the human closes it after acting on the findings; the loop never closes a spike itself. If the findings spawn build work, name it in the comment and let the user file or pick it.
11. **Blocked or awaiting-human issues get handed back via `needs-human-review`.** When an issue turns out to be blocked by something the loop genuinely cannot do (login credentials, an external approval, access it doesn't have), or an investigation/spike produced results a human must act on, post a comment on the issue stating the blocker or findings, add the `needs-human-review` label (bright orange; create it if missing), and move on. The issue comment + label is the invariant — the queue signal lives on the issue board. **Additionally, iff a partial implementation exists**, don't strand it: push the branch, open a draft PR (`Closes #N`), tag the PR `needs-human-review` too, and link it from the issue comment — the human reviews real code, not prose describing it. No diff (findings-only, blocked before code) → no PR. Treat `needs-human-review` like `skip-me` until a human clears it. Rules 10 and 11 are the standing, explicit exceptions to the loop's otherwise never-post-to-GitHub rule — scoped to spike findings and blocker/findings hand-backs only.

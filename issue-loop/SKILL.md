# Issue loop

Act as coordinator for the repo given as the argument. Pull open issues and sort them into the execution queue by four keys, in order:

1. **Version** — current-version labels first (e.g. `v1` when v1 is the launch scope); later versions (`v2`) and `maybe-*` candidates wait unless the user pulls them in.
2. **Bug** — `bug`-labeled issues first within a version.
3. **Priority** — P0 → P1 → P2 within that (no priority label = P2).
4. **Filed date** — oldest first as the tiebreak.

Run two at a time via codex-implementation → codex-review. Open PRs, merge automatically, watch deploys, continue until paused or empty. **Every 2 completed issues, re-pull the open board and re-sort before picking the next** — the user refiles and relabels mid-loop; a queue computed at session start is stale by definition.

## Roster (pinned — this loop's execution style)

- **The session's main agent holds the coordinator seat — whatever model it is** (fable usually; opus by choice): scopes each issue, writes the implementer prompts, reads every diff, arbitrates review findings, merges, keeps the trail. The coordinator never implements — about to edit app code beyond a trivial review fix (~5 lines)? Stop: that's a codex prompt, not your edit.
- **codex (gpt-5.6-terra) implements by default — UI issues included**, via `codex exec` per the codex-implementation skill — fast, clean, cheap. This holds no matter which model coordinates. UI issues verify via statics/build and the coordinator's diff read — never open a browser (`codex-computer-use`, Playwright, or otherwise) unless the user asks for it during the session; when they do, the coordinator judges the screenshots against the mocks and iterates until they clear the taste bar. Dispatch an opus-4.8 subagent only when taste must drive generation itself (net-new design, copywriting) — still dispatched, never the coordinator inline.
- **Review, big diffs**: a fresh ephemeral codex run with an adversarial prompt — it did not write the code, it's told to attack a specific checklist (correctness, scale smells, the issue's acceptance criteria). Same model, fresh context; independence comes from the framing. **Review, small diffs**: fable or opus reads them directly. Either way the coordinating model verifies reviewer claims before acting — reviews and their test assertions can encode wrong expectations.
- Everything else the global instructions cover — code style, taste, PR/commit conventions, the fresh-context review rule — still governs; don't restate or relitigate it per issue.

## Before beginning

If you keep a session log or a project workspace, attach this run to it before starting — that's where rule 9's trail lands. The loop dispatches implementation and review through the [codex skills](https://github.com/daytonbaird/fable-codex-coordinator); install those first.

**Establish the version before the first pick.** The queue's top sort key is the version label, so a run that guesses it burns down the wrong scope. If the user didn't name one, ask which version is in scope and whether later-version or `maybe-*` items should be pulled in. State the answer back before starting, and re-confirm on any board re-pull that surfaces a version label you haven't seen.

## Rules

1. **The queue is law.** The version → bug → priority → date sort above, two in flight. Never touch issues labeled `skip-me` or explicitly parked by the user. Also skip **pre-launch items** — issues whose action is timed to launch (title/body says "before launch", "at launch", "until launch", or the work only makes sense as a launch step, e.g. clearing data or flipping a disabled feature on) — unless the user pulls them in during the session. One issue = one branch = one PR (`Closes #N`). The user must always be able to tell what's being worked on.
2. **Read each issue fresh from GitHub at dispatch time** — issues get edited; your memory of the backlog is stale by definition.
   - **Steer around other agents' lanes.** Before claiming, read the issues other agents have claimed (`in-progress` you didn't set). If your candidate plausibly touches the same files or surface as one of those (same route file, same view, same subsystem), pass over it silently — no label, no comment — and take the next queue item. Re-check on every board re-pull; a passed-over issue becomes eligible again once the conflicting claim clears.
   - **Claim before you touch.** Multiple agents may run this loop on the same repo concurrently. The moment you pick an issue — before the worktree, before the prompt — add the green `in-progress` label (create it once if missing: color `0E8A16`, description "An agent is actively working this issue — do not pick up"). An issue already labeled `in-progress` belongs to another agent: treat it exactly like `skip-me`, never audit or "check on" it. Remove the label whenever the issue leaves your hands — a `needs-human-review` hand-back, a park, an abandon, and also on completion: when a merged `Closes #N` closes the issue, strip `in-progress` right after the merge so closed issues never carry a stale claim. A claim you're no longer actively working is a lie — clean it up before ending the session or writing a handoff.
3. **Fresh worktree per issue, off `origin/main`.** Never work in the main checkout. Follow the repo's documented setup order.
4. **The implementer gets a self-contained prompt**: repo context, acceptance criteria from the issue, the repo's standing constraints and known footguns, exact verification commands, a report-file path. Global preferences carry into codex on their own; repo-specific context does not. A vague prompt costs a full round trip. **If the repo keeps topic docs (a `docs/` dir, an AGENTS.md "keep docs true" rule), the prompt names the docs the change plausibly touches and requires updating them in the same diff** — implementers never update docs unprompted, and the coordinator checks doc truth at review: a behavior change that contradicts a documented claim is a review finding, same severity as a failing test.
5. **One test-harness owner at a time.** If the repo's e2e suite binds fixed ports, only one concurrent run may use it; the other runs static checks and the coordinator runs its suite serially before merge.
6. **Every diff gets adversarial review per the roster** — fresh-context codex pass with an attack checklist for big diffs, fable or opus directly for small ones, with the coordinating model verifying reviewer claims always. Review findings go back to a codex fix pass or get fixed inline; re-verify after.
7. **Serial merges; watch every deploy to completion.** A green merge means nothing until CI finishes. If two branches touched generated files, regenerate on merged main and run the combined suite once.
8. **P0s break every rule except verification.** Fix inline if fastest, but reproduce the exact failing condition before and after — never ship a P0 fix on reasoning alone.
9. **Leave a trail as you go** — session log per landing, durable lessons to agent memory. The loop survives sessions only if the state does.
10. **Spike tickets resolve as a comment on the issue.** A `spike`-labeled issue is a research dispatch (read-only codex), not a build — no branch, no PR. The deliverable is a findings comment posted on the issue itself: answers with file:line citations, verified-vs-inferred distinguished, and any questions that still need a human owner. When the findings comment is posted, tag the issue `needs-human-review` and move on — the human closes it after acting on the findings; the loop never closes a spike itself. If the findings spawn build work, name it in the comment and let the user file or pick it.
11. **Blocked or awaiting-human issues get handed back via `needs-human-review`.** When an issue turns out to be blocked by something the loop genuinely cannot do (login credentials, an external approval, access it doesn't have), or an investigation/spike produced results a human must act on, post a comment on the issue stating the blocker or findings, add the `needs-human-review` label (bright orange; create it if missing), and move on. The issue comment + label is the invariant — the queue signal lives on the issue board. **Additionally, iff a partial implementation exists**, don't strand it: push the branch, open a draft PR (`Closes #N`), tag the PR `needs-human-review` too, and link it from the issue comment — the human reviews real code, not prose describing it. No diff (findings-only, blocked before code) → no PR. Treat `needs-human-review` like `skip-me` until a human clears it. Rules 10 and 11 are the standing, explicit exceptions to the loop's otherwise never-post-to-GitHub rule — scoped to spike findings and blocker/findings hand-backs only.
